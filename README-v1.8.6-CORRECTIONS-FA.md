# اصلاح دستی ورود و خروج — نسخهٔ ۱.۸.۶ (کاندیدا)

> **این بسته روی Production نصب نشده است.** سرور فعلی پس از استقرار موفق ۱.۸.۵ همچنان باید با همان نسخه کار کند تا Migration و تست نسخهٔ جدید تأیید شود.

## تجربهٔ مدیر

منوی جدید **«اصلاح تردد»** فقط به مدیر (`admin`) نمایش داده می‌شود. مدیر کارمند را بر اساس **شناسهٔ یکتای دستگاه** انتخاب می‌کند، تاریخ **شمسی** را وارد می‌کند، ثبت‌های واقعی دستگاه و ساعت‌های مؤثر را می‌بیند و سپس:

1. اگر **ورود فراموش شده** و مثلاً تنها ثبت ۱۶:۰۰ موجود است، در «ورود اصلاحی» مقدار `08:00` را می‌نویسد و خروج را خالی می‌گذارد. در گزارش روزانه ساعت‌های ۰۸:۰۰ تا ۱۶:۰۰ و مدت ۰۸:۰۰ درج می‌شوند.
2. اگر **خروج فراموش شده** و تنها ثبت ۰۸:۰۰ موجود است، فیلد ورود را خالی و «خروج اصلاحی» را `16:00` وارد می‌کند.
3. اگر **هیچ ثبت دستگاهی وجود ندارد**، برای اضافه کردن روز حضور هر دو ساعت را وارد می‌کند. این روز فقط در گزارش «تمام گزارش‌ها» نمایان می‌شود و به یک فایل DAT نامرتبط نسبت داده نمی‌شود.
4. اگر ورود/خروج ثبت‌شده اشتباه است، می‌تواند یکی یا هر دو ساعت را جایگزین کند. ساعت‌های اصلاحی باید مربوط به همان تاریخ محلی و به ترتیب ورود < خروج باشند؛ **شیفت شب بین دو روز در این نسخه پشتیبانی نمی‌شود**.
5. هر ثبت یا بازنگری یک **نسخهٔ جدید** در تاریخچه می‌سازد: شناسه کارمند، روز، ساعت‌های اصلاحی، دلیل الزامی، شناسه مدیر و زمان ثبت. ویرایش قبلی پاک نمی‌شود.
6. برای بازگشت به ثبت‌های اولیه، مدیر **«لغو اصلاح»** را با ذکر دلیل می‌زند؛ این نیز یک رویداد جدید است و سابقه باقی می‌ماند.

در جدول «گزارش حضور»، روزهای دارای اصلاح با نشان **«✎ اصلاح مدیر»** مشخص می‌شوند. مدیر از لینک «اصلاح تردد» همان ردیف می‌تواند اصلاح کند. افراد غیرمدیر اجازهٔ ورود به صفحه یا تغییر سوابق را ندارند.

## اثر بر گزارش‌ها

- روزانه: ساعت اول/آخر **مؤثر** و فاصلهٔ زمانی آن‌ها جایگزین مقادیر محاسباتی می‌شود؛ تعداد ثبت، تعداد واقعی ثبت‌های دستگاه می‌ماند.
- ماهانه شمسی، سالانه شمسی، دورهٔ شناور و بازهٔ دلخواه: همه از همان ساعت‌های مؤثر روزانه جمع می‌شوند. روزهای اصلاح‌شدهٔ معتبر دیگر «ناقص» محسوب نمی‌شوند.
- **تمام ثبت‌های خام** و **جفت ثبت‌های متوالی**: دادهٔ دستگاه تغییر نمی‌کند؛ اصلاح صرفاً برای محاسبات است.
- Excel همان محاسبات صفحه و همان چیدمان ستون‌های ۱.۸.۵ را حفظ می‌کند.
- اگر کاربر «یک فایل نام‌گذاری‌شده» را فیلتر کند، اصلاح فقط بر روزهایی اعمال می‌شود که در همان فایل وجود دارند؛ روز تماماً دستی در گزارش همان فایل درج نمی‌شود.
- تغییرات مستقل از نام نمایشی کارمند و مبتنی بر `employee_id` هستند؛ دو کارمند همنام ادغام نمی‌شوند.

**تفسیر:** این اعداد فاصلهٔ اولین تا آخرین زمان ثبت‌شده/اصلاحی هستند، نه ساعات حقوق و دستمزد تأییدشده. ناهار، خروج موقت، اضافه‌کار، مرخصی، شیفت شب و محاسبهٔ قرارداد نیازمند سیاست مستقل هستند.

## طراحی و امنیت

- مدل `AttendanceCorrection` در جدول جدید `attendance_corrections`؛ فقط رویدادهای **`set` و `revoke`** ذخیره می‌شوند. آخرین رویداد هر کارمند/روز اعمال می‌شود.
- **هیچ UPDATE یا DELETE** روی `report_punches`، `attendance_logs`، `attendance_records`، `report_days` و DAT انجام نمی‌شود.
- متدهای POST به RBAC `admin`، توکن CSRF و **دلیل ۵ تا ۵۰۰ نویسه** محدودند. تاریخ آینده، ساعت نامعتبر، مدت منفی/صفر و روز بی‌ثبت با یک ساعت اصلاحی مردودند.
- `SELECT FOR UPDATE` روی کارمند به‌همراه `expected_revision`، ثبت هم‌زمان از دو تب را با کد HTTP 409 متوقف می‌کند.
- رویداد خلاصهٔ تغییر در `audit_logs` هم ثبت می‌شود. تاریخچهٔ صفحه ۱۰۰ نسخهٔ اخیر را نشان می‌دهد؛ جدول تمام نسخه‌ها را نگه می‌دارد.
- هیچ رمز، CA خصوصی، `.env`، دادهٔ کارمند یا فایل خام دستگاه در این آرشیو نیست.

## Migration مورد نیاز — توقف اجباری پیش از استقرار وب

**نسخهٔ ۱.۸.۶ برخلاف ۱.۸.۵ یک Migration واقعی دارد. از دستور استقرار وب ۱.۸.۵ برای این تغییر استفاده نکنید.**

فایل جدید: `app/migrations/versions/0002_attendance_corrections.py`، بر پایهٔ revision `0001_initial`.

Migration فقط جدول و ایندکس جدید و چند constraint اضافه می‌کند؛ جدول‌های قبلی و داده‌هایشان را تغییر نمی‌دهد. وب جدید در Startup، وجود جدول تازه را بررسی می‌کند. اسکریپت CI/Release نیز **پیش از هر جایگزینی وب**، به‌صورت read-only وجود جدول و ثبت `alembic_version = 0002_corrections` را در دیتابیس Production بررسی می‌کند و در غیر این صورت Deployment را متوقف می‌کند. در این نسخه، اجرای Migration **خودکار نشده** است.

روند امن مورد نیاز:

1. **بررسی فقط‌خواندنی**: نسخهٔ فعلی Migration، جدول‌ها، محیط اجرای PostgreSQL مستقل و سلامت همه سرویس‌ها را ثبت کنید. اگر `alembic_version` غایب است یا مقدار آن `0001_initial` نیست، توقف و بررسی DBA الزامی است؛ `alembic stamp` کورکورانه انجام ندهید.
2. **بکاپ معتبر و تست Restore** از PostgreSQL قبل از هر DDL، با نگهداری نسخهٔ پیشین image و release pointer. تا وقتی Restore آزموده نشده است، Migration مجاز نیست.
3. ساخت image کاندیدا در Jenkins از GitLab، اجرای کل تست‌های offline و سپس اجرای **Migration روی دیتابیس Staging کپی‌شده**؛ بررسی شمارش و سلامت داده‌ها، نقش‌های کاربری، تاریخچه، Excel و آزمون مرورگر در هر دو تم.
4. در پنجرهٔ تغییر مجاز و با تأیید صریح اپراتور، اجرای `alembic upgrade 0002_corrections` با image و محیط DB تعریف‌شده، **فقط روی دیتابیس هدف تأییدشده**؛ ثبت revision و بررسی سلامت سرویس‌های فعلی.
5. اجرای preflight کاندیدای CI/Release و سپس تأیید دستی Jenkins برای جایگزینی **فقط وب** با image دارای Digest از Nexus. `postgresql`، `attendance-rustfs` و `pg-exporter`، حجم‌های داده، `.env` و Composeهای اصلی نباید بازآفرینی شوند.
6. Smoke: `/health=200`, `/login=200`, `GET /corrections=401` برای مهمان، ۴۰۳ برای غیرمدیر، ارسال اصلاح و لغو روی دادهٔ تست، یکسان بودن خروجی Excel و صفحه، بررسی HTTP و CSP و Audit.

اگر وب جدید مشکل داشت، **فقط وب** و release pointer به نسخهٔ ۱.۸.۵ بازگردند؛ جدول افزودهٔ correction و تاریخچه حذف نشوند. `downgrade()` برای جلوگیری از حذف سابقه عمداً غیرفعال است.

### بررسی فقط‌خواندنی قبل از درخواست مجوز تغییر Production

روی همان میزبان Production و بدون چاپ رمز یا تنظیمات اتصال:

```bash
cd /home/devops/containerd/devops/attendance-backend/attendance-system

docker inspect attendance-web-1 --format 'IMAGE={{.Config.Image}} HEALTH={{.State.Health.Status}}'

docker exec attendance-web-1 python -c '
from sqlalchemy import inspect, text
from main import engine
with engine.connect() as db:
    tables = set(inspect(db).get_table_names())
    print("CORRECTIONS_TABLE_EXISTS=", "attendance_corrections" in tables)
    if "alembic_version" in tables:
        print("ALEMBIC_VERSION=", db.execute(text("SELECT version_num FROM alembic_version")).scalars().all())
    else:
        print("ALEMBIC_VERSION_TABLE=MISSING")
'
```

خروجی این بررسی **هیچ تغییری** در Production ایجاد نمی‌کند؛ اما وضعیت واقعی Migration را برای طرح استقرار مشخص می‌کند.

## آزمون نسخهٔ کاندیدا

تست‌های مستقل قابل اجرا روی میزبان بدون دسترسی DB:

```bash
python3 -m py_compile app/main.py ci/remote_release.py app/migrations/versions/0002_attendance_corrections.py
python3 -m unittest discover -s tests -p 'test_*stdlib.py' -v
python3 -m unittest discover -s tests -p 'test_ci_release.py' -v
node tests/test_report_sort.cjs
node tests/test_presence_duration_sort.cjs
python3 scripts/check_project.py .
```

**تست‌های کامل** با SQLAlchemy، Jdatetime و بقیه وابستگی‌های ثابت‌شدهٔ `app/requirements.txt` باید روی image جدید، در **محیط منزوی بدون شبکه/پایگاه‌داده Production** اجرا شوند:

```bash
python -m unittest discover -s tests -p 'test_*.py' -v
```

تست‌های جدید `test_attendance_corrections.py` روی دیتابیس موقت SQLite با `Base.metadata.create_all` ساخته می‌شوند و به دیتابیس واقعی وصل نمی‌شوند. این تست **جایگزین اجرای Alembic روی کپی PostgreSQL واقعی نیست**.

**وضعیت انتشار:** `Candidate / Not deployed`. بدون گرفتن نتیجهٔ کنترل‌های DB و مجوز تغییر، هیچ دستور DDL یا `docker compose up` روی Production اجرا نکنید.
