## نیاز و رفتار

برخی مدیران معاف از دستگاه حضور و غیاب هستند. منشی شرکت باید بدون دسترسی به مدیریت
کارکنان، Import یا اصلاح تردد دیگران، برای یک مدیر و یک **تاریخ شمسی**، هر دو ساعت ورود
و خروج را ثبت کند. گزارش روزانه، ماهانه، سالانه و دوره‌ای موجود باید همان داده را ببیند،
در حالی که لاگ دستگاه و فایل DAT اولیه بدون تغییر بمانند.

## مسیرها

- `GET /managers/attendance`: صفحه اختصاصی منشی و ادمین؛ انتخاب مدیر، تاریخ و مشاهده تاریخچه.
- `POST /managers/attendance/save`: ایجاد نسخهٔ جدید از حضور همان روز.
- `POST /managers/attendance/revoke`: لغو نسخهٔ فعال بدون حذف تاریخچه.
- `POST /employees/{id}/attendance-group`: تغییر گروه یک فرد، فقط با نقش `admin` و دلیل.
- `POST /employees`: پشتیبانی از `attendance_group=management`؛ اگر شماره دستگاه مدیر خالی باشد،
  شناسهٔ پایدار یکتای `MANUAL-...` تولید می‌شود. برای کارمند عادی شماره دستگاه اجباری است.
- `POST /users`: امکان ساخت حساب با نقش `secretary` توسط ادمین.

هنگام ورود با نقش منشی، صفحه اصلی به `/managers/attendance` هدایت می‌شود و
منوی کاربری فقط همان بخش را نشان می‌دهد. کنترل مجوز برای هر مسیر در سرور انجام می‌شود،
نه صرفاً در منو.

## قواعد داده و ایمنی

1. فقط `Employee.status=active` و `Employee.attendance_group=management` انتخاب می‌شوند.
2. هر دو ساعت ورود و خروج لازم‌اند؛ خروج باید بعد از ورود و در همان روز باشد؛ تاریخ آینده ممنوع است.
3. زمان با منطقه زمانی `Asia/Tehran` تفسیر و به UTC در PostgreSQL ذخیره می‌شود.
4. هر تغییر با شناسه ثابت کارمند، دلیل حداقل ۵ نویسه، شناسهٔ ثبت‌کننده، زمان و نسخه ذخیره می‌شود.
5. سازوکار `expected_revision` و قفل رکورد کارمند، فرم هم‌زمان/قدیمی را با HTTP 409 رد می‌کند.
6. اگر آن روز تردد دستگاهی یا اصلاح اداری غیرمنشی داشته باشد، مسیر منشی با HTTP 409 رد می‌شود؛ بررسی با ادمین است.
7. ثبت با `AttendanceCorrection.origin=manager_manual` در دیتای موجود ظاهر می‌شود؛
   `ReportPunch`، `Log`، `Import` و `ReportDay` تغییر نمی‌کنند. در گزارش فایل نام‌دار، روز
   فقط‌دستی ظاهر نمی‌شود؛ در حالت «تمام گزارش‌ها» ظاهر می‌شود.
8. گزارش روزانه برچسب «ثبت دستی مدیران» را نشان می‌دهد و تعداد ثبت دستگاه صفر است.
   مقادیر گزارش برای حقوق و دستمزد به‌صورت خودکار تأییدشده محسوب نمی‌شوند.
9. CSRF، RBAC، جلوگیری از XSS، no-store و noindex از سازوکار موجود تبعیت می‌کنند.

## مهاجرت فقط روی staging

فایل `app/migrations/versions/0004_management_manual.py` شامل فقط دو ستون افزایشی است:

- `employees.attendance_group NOT NULL DEFAULT 'staff'`؛ تمام رکوردهای قبلی «عادی» می‌مانند.
- `attendance_corrections.origin NOT NULL DEFAULT 'admin_correction'`؛ تمام اصلاحات قبلی برچسب قبلی می‌گیرند.

همچنین دو Check Constraint و Index گروه اضافه می‌شود. هیچ UPDATE/DELETE و DROP نداریم.
`downgrade` عمداً بسته است تا تاریخچه و طبقه‌بندی اشخاص از بین نرود.

پیش از اجرای staging لازم است نسخهٔ درست schema، وضعیت backup و restore-test مشخص شوند.
روی Production هیچ فرمان migration یا deploy را بدون تأیید جداگانه اجرا نکنید.

## تست‌های لازم

کاندیدهای تست: `tests/test_managers_manual_attendance.py` و تست‌های قبلی پروژه.

1. مهاجرت 0001→0002→0003→0004 روی PostgreSQL خالی و سپس مهاجرت 0003→0004 روی نسخهٔ
   کپی‌شدهٔ staging؛ شمارش داده‌های قبل/بعد و restore-test.
2. با حساب منشی، ثبت تردد مدیر بدون دستگاه، ویرایش دوباره و لغو با تاریخچه؛ تأثیر گزارش
   روزانه، ماهانه، سالانه و Excel یکسان باشد.
3. تست‌های منفی: 401/403، CSRF، کارمند عادی یا تعلیق‌شده، تاریخ/ساعت نامعتبر، تاریخ آینده،
   تکرار هم‌زمان، تردد دستگاهی، اصلاح ادمین، غیرفعال‌سازی حساب، XSS.
4. Browser QA در 360/768/1440 پیکسل، Light/Dark و RTL، دسترسی کیبورد و زوم ۱۰۰٪.
5. پس از تست‌های موفق، ارزیابی امنیت، concurrency، backup/rollback و تصمیم انتشار جداگانه.
