# R7.1 — محافظت ورود (Development / QA)

این تغییر فقط برای ارزیابی و آزمایش ایزوله آماده شده است. **هیچ Migration، استقرار، Push یا تغییری روی Production مجاز نشده است.** دیتابیس مستقل موجود PostgreSQL 18 و وب Production را از راه‌اندازی‌های QA جدا نگه دارید.

## رفتار

- قفل موقت حساب پس از **۵ تلاش ناموفق** در یک بازهٔ **۱۵ دقیقه‌ای**؛ مبدأ IP تغییری در بودجه حساب ایجاد نمی‌کند.
- محدودیت جداگانه **۳۰ خطای ورود از یک IP** در ۱۵ دقیقه برای مقابله با حملات نام‌های کاربری متنوع. مقدار ۳۰ برای کاهش احتمال اختلال کاربران پشت NAT/Proxy است.
- تلاش عبور از سقف و تلاش‌های بعدی تا پایان قفل، HTML فارسی با وضعیت `429` و هدر `Retry-After` دریافت می‌کنند. ورود صحیح نیز تا پایان قفل مجاز نیست.
- برای نام کاربری موجود، غیرموجود و غیرفعال مسیر اعتبارسنجی رمز پرهزینه یکسان است؛ پیام خطا وجود حساب را مشخص نمی‌کند.
- شمارنده‌ها در جدول `login_rate_limits` با `HMAC-SHA256` و `SESSION_SECRET` کلیدگذاری می‌شوند. نام کاربری، رمز و IP خام در جدول یا رخداد `login_failed` ذخیره نمی‌شوند.
- PostgreSQL به کمک `INSERT ... ON CONFLICT DO NOTHING` و `SELECT ... FOR UPDATE`، افزایش شمارنده را بین Workerها سریالی می‌کند. SQLite فقط برای تست‌های منفرد درون‌حافظه‌ای است.
- تلاش‌های ناموفق با `login_failed`، عبور از سقف با `login_rate_limited` و ورود موفق با `login` در Audit ذخیره می‌شوند.
- ورود موفق فقط شمارنده حساب را صفر می‌کند، نه بودجه خطاهای IP.

تنظیمات قابل تغییر در محیط اجرا، بدون تغییر کد:

| متغیر | پیش‌فرض |
|---|---:|
| `LOGIN_WINDOW_SECONDS` | `900` |
| `LOGIN_LOCK_SECONDS` | `900` |
| `LOGIN_ACCOUNT_FAILURES` | `5` |
| `LOGIN_IP_FAILURES` | `30` |
| `LOGIN_COUNTER_RETENTION_DAYS` | `7` |

برای محیط عملیاتی باید مقدار `SESSION_SECRET` تصادفی و پایدار باشد؛ تغییر آن نشست‌ها و کلیدهای شمارنده را تغییر می‌دهد و عملاً بودجه‌های قبلی قابل شناسایی نخواهند بود.

## Migration

`0006_login_throttling` فقط جدول `login_rate_limits` با یک ایندکس را می‌سازد؛ هیچ اطلاعات کارکنان، کاربران، تردد، گزارش یا تأیید مدیران حذف یا ویرایش نمی‌شود. `downgrade()` برای حفظ سابقهٔ امنیتی عمداً ممنوع است. Rollback وب به Image قبلی با باقی‌ماندن جدول اضافی سازگار است، ولی اجرای Migration روی Production نیازمند بکاپ آزموده و مجوز صریح است.

گارد `ci/remote_release.py` اکنون وجود جدول، ایندکس و Revision `0006_login_throttling` را **قبل از هر جایگزینی وب** کنترل می‌کند. بنابراین در محیط Production که هنوز روی `0005` است، انتشار جدید عمداً متوقف می‌شود.

## نگهداری جدول

پاکسازی جدول در Startup وب انجام نمی‌شود. در یک فرآیند مدیریتی مستقل و فقط بعد از تأیید اتصال صحیح دیتابیس و بکاپ:

```bash
python prune_login_throttle.py --dry-run
python prune_login_throttle.py --apply
```

اجرای این فرمان‌ها روی دیتابیس واقعی در این مرحله **مجاز نیست**؛ ابتدا در دیتابیس مصنوعی QA آزمایش کنید. وظیفهٔ زمان‌بندی و هشدار دربارهٔ رشد جدول باید قبل از Release نهایی تعیین شود.

## QA مورد انتظار

1. تست‌های واحد و امنیتی: `python -m unittest discover -s tests -p 'test_*.py'` در محیطی که dependencies نصب دارد.
2. تست ساختار سورس: `python scripts/check_project.py .`.
3. یک PostgreSQL 18 مستقل و مصنوعی جدید؛ اجرای `alembic upgrade head` و تأیید `0006_login_throttling`.
4. ایجاد کاربر مصنوعی، چهار ورود اشتباه با پاسخ `303`، پنجمین ورود با پاسخ `429`، ورود با رمز صحیح در حالت قفل با پاسخ `429`، پس از پایان قفل ورود صحیح با پاسخ `303`.
5. تست همزمانی چند Worker و محدودیت IP، پایداری شمارنده پس از Restart، و بررسی دقیق جلوگیری از افشای شناسه‌ها در Log و Audit.

## محدودیت‌های شناخته‌شده

- هویت IP از `request.client.host` گرفته می‌شود، نه هدر `X-Forwarded-For` ارسال‌شده توسط کاربر. در صورت وجود Reverse Proxy باید آدرس مبدأ واقعی فقط از Proxy قابل اعتماد به ASGI برسد و تنظیم `LOGIN_IP_FAILURES` متناسب با NAT بررسی شود.
- قفل حساب، هدف حملهٔ Denial-of-Service نیز می‌تواند باشد؛ مانیتورینگ، هشدار و رویهٔ پشتیبانی برای بازگشایی حساب باید قبل از Production تدوین شود.
- این کنترل تنها Login را پوشش می‌دهد. محدودسازی گزارش‌گیری، جست‌وجو، خروجی Excel و Upload به‌صورت مستقل در Release Gate باقی می‌مانند.
- تا انجام QA PostgreSQL واقعی، آزمون همزمانی، آزمون Browser موبایل و بررسی Rollback عملی، وضعیت `NOT PRODUCTION-READY` است.
