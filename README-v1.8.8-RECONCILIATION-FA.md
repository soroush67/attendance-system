# نسخهٔ آزمایشی v1.8.8-r1 — رفع مغایرت قبل از Import

این بسته **سورس کامل** نسخهٔ v1.8.8-r1 بر پایهٔ v1.8.7 است. هنوز برای Production مستقر یا تأیید نشده و تغییر دیتابیس عملیاتی بدون برنامهٔ مستقل، Backup تست‌شده و مجوز ممنوع است.

**اصلاح r1 پس از Smoke ناموفق:** نسخهٔ اولیهٔ v1.8.8 روی دیتابیس موقت SQLite در دو مورد شکست خورد؛ یک مورد مربوط به عدم درج برچسب «نام گزارش» در HTML و دیگری اختلاف `timezone-aware`/`timezone-naive` در تشخیص تردد ازپیش‌ثبت‌شده بود. هر دو در این Revision اصلاح شده‌اند؛ سازگاری نهایی با PostgreSQL 18 و تست HTTP هنوز باید مجدداً روی آزمایشگاه کاملاً ساختگی تأیید شود. ابزار آزمایش این Revision هویت و SHA256 جدا دارد.

## مسیر جدید کار

1. کاربر مجاز فایل DAT را از `/imports` آپلود می‌کند. فایل در `pending_imports` و تک‌تک سطرها در `pending_import_rows` ذخیره می‌شوند؛ در این لحظه هیچ `ReportPunch`، `attendance_logs`، `reports` یا جمع روزانه تغییر نمی‌کند.
2. صفحهٔ `/imports/staged/{id}` تمام سطرها را صفحه‌بندی‌شده نشان می‌دهد: شمارهٔ اصلی سطر، محتوای اصلی، کد دستگاه، زمان استخراج‌شده و نوع مغایرت.
3. سطر معتبر `ready` می‌شود. شناسهٔ ناشناس، زمان نامعتبر، سطر تکراری در فایل و تردد موجود در دیتابیس به وضعیت `pending` می‌روند.
4. مدیر با نقش `admin` برای هر مغایرت تصمیم ثبت می‌کند و **دلیل ۵ تا ۵۰۰ نویسه‌ای** می‌نویسد. برای شماره ناشناس می‌تواند آن را به یک کارمند موجود نگاشت کند؛ فرمت نامعتبر و تکرارها فقط با دلیل رد می‌شوند. هر تصمیم در `audit_logs` ثبت می‌شود و اصل متن سطر باقی می‌ماند.
5. دکمهٔ «تأیید نهایی و Import به دیتابیس» فقط زمانی نشان داده می‌شود که هیچ `pending` باقی نمانده باشد؛ Backend نیز مستقل از UI این شرط را کنترل می‌کند.
6. Commit با یک Transaction اجرا می‌شود؛ پیش از نوشتن، شناسهٔ کارکنان، نگاشت‌ها، تکرارهای داخلی و تغییرات هم‌زمان دیتابیس مجدداً بررسی می‌شوند. سپس `imports`، `report_sets`، `report_days`، `report_punches`، `attendance_logs` و جمع‌بندی‌های روزانه ثبت می‌شوند. خطای هم‌زمانی Commit را متوقف می‌کند.
7. داده‌های تأییدشده از مسیرهای موجود `/reports` و `/reports/download` قابل مشاهده‌اند. فایل‌های قدیمی و اصلاحات دستی نسخهٔ v1.8.7 حفظ می‌شوند.

## محدودیت‌ها (مهم)

- این نسخه **فاز اول** معماری «دیتابیس مرکزی و رفع مغایرت» است. گزارش‌ها همچنان از `report_sets/report_days/report_punches` به‌علاوهٔ اصلاحات دستی ساخته می‌شوند. تبدیل کامل هویت ردیف‌های گزارش از `device_id` به `employee_id`، نگاشت تاریخی شماره دستگاه‌ها، حذف وابستگی محاسبات به نام گزارش و یک Query واحد مرجع هنوز کار بعدی‌اند.
- تصمیم‌های جدید تا قبل از Commit قابل تغییرند؛ تغییر تصمیم در جدول `Audit` ثبت می‌شود. رکوردهای خام قدیمی و اصلاحات تاریخی حذف نمی‌شوند.
- برای افزایش امنیت و پاسخ‌گویی، حداکثر حجم DAT ده مگابایت و حداکثر تعداد سطر بیست هزار است؛ فایل بزرگ‌تر صریحاً رد می‌شود و هیچ سطری بی‌اطلاع حذف نمی‌شود.
- نقش `operator` اجازهٔ Upload و مشاهدهٔ صف را دارد؛ تأیید تصمیم، لغو و Import نهایی فقط در اختیار `admin` است.
- داده‌های Stage از خود DB ذخیره و رهگیری می‌شوند. در Production باید سیاست Retention، Backup، و حذف امن داده‌های Stage به‌صورت مجزا تصویب شود.
- هم‌زمانی خاص دو فایل با نام یکسان، کارایی ۲۰هزار سطر و آزمون‌های بار/Accessibility نیازمند گیت‌های بعدی هستند.

## Migration

Migration جدید `0003_reconciliation` کاملاً **Additive** است و فقط دو جدول و دو Index جدید اضافه می‌کند. پشتیبانی از `downgrade` تخریبی عمداً بسته است. Migration باید ابتدا در PostgreSQL 18 کاملاً **ساختگی** اجرا شود؛ تحت هیچ شرایطی مستقیم روی دیتابیس Production اجرا نکنید.

## بررسی فقط‌خواندنی سورس

```bash
python3 -m py_compile app/main.py app/migrations/versions/0003_pending_import_reconciliation.py
python3 scripts/check_project.py .
```

## آزمون عملیاتی در محیط کاملاً جدا

بستهٔ `attendance-v188r1-staging-lab.zip` جداگانه داده می‌شود. با imageهای کش‌شدهٔ Docker موجود، شبکهٔ `--internal` بدون Port Publish و PostgreSQL 18 جدید کار می‌کند. ابتدا `preflight` و سپس `smoke` با تأیید تعاملی `STAGE-LAB-v1.8.8-r1` اجرا شود. **تنها پس از PASS تمام مراحل** می‌توان سراغ مرور ظاهر صفحه در مرورگر و برنامهٔ انتشار رفت.
