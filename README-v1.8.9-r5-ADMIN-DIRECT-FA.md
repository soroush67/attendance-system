# سامانه حضور و غیاب — v1.8.9-r5، ثبت مستقیم مدیران توسط ادمین

**DEV Candidate / NOT PRODUCTION-READY.** این بسته از نسخهٔ کامل `v1.8.9-r4` مشتق شده است؛ هیچ دستور نصب خودکار، تغییر Production یا اتصال به دیتابیس واقعی در بسته اجرا نشده است.

## تصمیم کارفرما: حالت سوم

فقط یک **حساب ادمین (`admin`)** برای مدیریت کاربران، تعریف افراد عضو گروه مدیران و ثبت ساعات حضور آنان نیاز است. **مدیرِ مشمول تردد (`Employee.attendance_group=management`) حساب Login لازم ندارد**. ثبت دستی یا واردکردن Excel توسط ادمین در همان تراکنش روی گزارش‌های نهایی اثر می‌گذارد و نیازی به تأیید دومرحله‌ای ندارد.

## مسیرهای رابط کاربری

1. با حساب `admin` وارد شوید.
2. از `/employees` مدیر را با گروه «مدیران · ثبت دستی توسط ادمین» تعریف کنید؛ برای فرد بدون اثرانگشت، کد دستگاه می‌تواند خالی باشد تا شناسهٔ `MANUAL-...` ایجاد شود.
3. از `/managers/attendance` مدیر و تاریخ شمسی را انتخاب و ساعت ورود/خروج و دلیل را وارد کنید؛ دکمهٔ «ثبت مستقیم در گزارش» فوراً یک **نسخهٔ افزایشی** در `attendance_corrections` ذخیره می‌کند.
4. برای حداکثر ۲۵ مدیر در یک نوبت، از `/managers/attendance/bulk` استفاده کنید؛ در صورت خطای یک سطر، کل عملیات رد می‌شود.
5. برای چند مدیر در چند روز، در همان صفحه قالب Excel را دانلود کنید، هر مدیر/روز را در یک سطر پر کنید و بارگذاری نمایید. تا **۱۰۰۰ ردیف و ۲ مگابایت** در یک فایل، با اعتبارسنجی اتمیک. فایل واقعی و اطلاعات محرمانه را در محیط آزمایشی وارد نکنید.
6. برای لغو ثبت مدیر در یک روز، از فرم «لغو ثبت مستقیم» استفاده کنید. سابقهٔ اصلی پاک نمی‌شود؛ یک نسخهٔ جدید با `action=revoke` ایجاد می‌شود.

## قواعد ایمنی و سازگاری

- فقط نقش `admin` می‌تواند بلافاصله ثبت تکی، گروهی و Excel را در گزارش اعمال کند. `viewer`, `operator`, `exporter` اجازهٔ این مسیرها را ندارند.
- نقش قدیمی `secretary` و صف دومرحله‌ای هنوز برای سازگاری حفظ شده‌اند، اما در گردش کار جدید کارفرما استفاده نمی‌شوند. درخواست‌های `pending` موجود **خودکار تأیید، لغو یا حذف نمی‌شوند** و برای جلوگیری از تداخل جلوی ثبت مستقیم همان مدیر/روز را می‌گیرند.
- ثبت خام دستگاه و `report_punches` تغییر نمی‌کنند. روز دارای پانچ دستگاهی یا اصلاح اداری نامرتبط از ثبت مستقیم مدیران کنار گذاشته می‌شود.
- در ثبت تکی، اصلاح ثبت قبلی مدیر با `expected_revision` کنترل و به‌صورت append-only نگهداری می‌شود. ثبت گروهی و Excel فقط روزهای بدون اصلاح قبلی را می‌پذیرند؛ برای اصلاح روز موجود از ثبت تکی استفاده کنید.
- ساعت ورود باید قبل از ساعت خروج و در همان روز باشد؛ روز آینده، مدیر معلق/حذف‌شده، کد ناشناخته، تکرار مدیر/روز و فرمول Excel رد می‌شوند.
- هر عملیات دارای احراز هویت، RBAC سرور، CSRF، Audit actor و دلیل اجباری است. یک فایل نامعتبر یا متداخل هیچ رکوردی اضافه نمی‌کند.
- **بدون Migration جدید**؛ جدول‌های نسخهٔ `0005_manager_approvals` کافی‌اند و جدول `attendance_corrections` با `origin=manager_manual` برای ثبت مستقیم استفاده می‌شود.
- عنوان مبهم نقش `admin` در UI از «مدیر» به «مدیر سیستم / ادمین» تغییر کرده است.

## تست و Release Gate

```bash
python3 scripts/check_project.py .
python3 -m compileall -q app tests
docker-compose --env-file .env.example -f compose.app.yml config --quiet
docker-compose --env-file .env.example -f compose.database.yml config --quiet
```

در محیط آزمایشی مجهز به وابستگی‌های Python، تست‌های جدید:

```bash
PYTHONPATH=app DATABASE_URL='sqlite+pysqlite:///:memory:' SESSION_SECRET='local-synthetic-test' \
  python3 -m unittest discover -s tests -p 'test_admin_direct_attendance.py' -v
```

همچنین تست‌های قدیمی `test_managers_manual_attendance.py` و `test_manager_excel_parser.py` باید بدون رگرسیون اجرا شوند. اجرای سناریو روی PostgreSQL 18.4 **فقط با دیتابیس ساختگیِ مجزا** و مرورگر Private Tunnel مجاز است؛ نتایج این تست‌ها تا زمان اجرا باید `UNKNOWN` ثبت شوند.

قبل از انتشار روی Production: تست PostgreSQL/HTTP واقعی، بررسی UI، مهاجرت و سازگاری داده‌های واقعی، Backup+Restore، CI و Image Digest، rollback drill، بررسی مجوزها، اسکن امنیتی و تأیید صریح Change Management لازم است.
